# zabbix-victorialogs-delivery

Пара шаблонов Zabbix 7.0, которая отвечает на один вопрос: **доезжают ли логи хоста до VictoriaLogs.**

Не про здоровье самого VictoriaLogs — это отдельная задача. Здесь только доставка.

## Зачем

Два режима отказа, ради которых эта пара шаблонов и написана:

- Шиппер писал `Unauthorized` в собственный journald, читал journald сам себя и слал в никуда. Ошибки существовали три месяца и не покидали хост.
- Двух отправителей молча резал src-ACL на HAProxy. 62 дня тишины; дисковые буферы копили, потом всё проиграли заново с исходными временами.

Ни один не виден с отправляющей стороны. Оба видны с приёмной.

## Что внутри

| Шаблон | Где живёт | Что делает |
|---|---|---|
| `VictoriaLogs delivery by HTTP` | на хосте-приёмнике (один) | возраст последней записи по каждому отправителю, одним запросом LogsQL; список отправителей открывается из тех же данных |
| `Vector log shipper by Zabbix agent` | на каждом отправителе | состояние демона, счётчик его перезапусков, размер дискового буфера и контроль, что буфер вообще виден — только нативными ключами агента |

На отправителях не появляется ни одного файла: ни скрипта, ни UserParameter, ни правки конфига. Нужен Zabbix agent 2 — ради ключа `systemd.unit.info` — версии 7.0 или новее: агент постарше игнорирует поитемный таймаут и берёт `Timeout` из своего конфига (по умолчанию 3 с), чего не хватает на обход большого буфера.

## Как это устроено в одном абзаце

Отправители открываются **из самих данных**: каждая метка `host` в VictoriaLogs, прошедшая фильтр, становится наблюдаемым отправителем через минуту после первой строки — без группы хостов, без токена API и без шага регистрации, который можно забыть. Обычное возражение против обнаружения целей из наблюдаемого сигнала — «умерший хост исчезнет из данных вместе со своим алертом ровно тогда, когда проблема максимальна» — закрывается настройкой правила обнаружения, а не вторым реестром: потерянные ресурсы **никогда не отключаются** и удаляются только через 30 дней. Замолчавший отправитель сохраняет свой элемент, падает в сентинел и продолжает алертить. Свежесть считает сам VictoriaLogs: `now() - max(_time)` по каждой метке. Подробности и граф зависимостей — в [docs/architecture.md](docs/architecture.md).

## Установка

1. Импортировать оба шаблона из `template/`.
2. Привязать `VictoriaLogs delivery by HTTP` к хосту-приёмнику и поставить `{$VL.URL}`. Больше ничего обязательного: ни группы, ни пользователя, ни роли, ни токена — этот шаблон не обращается к API Zabbix вообще.
3. **Разобрать метки, которые уже лежат в хранилище**, и лишние внести в `{$LOG.LABEL.EXCLUDE}`. Это единственный шаг, который делается руками и только один раз. В окне `{$VL.WINDOW}` почти всегда обнаруживается мусор: разовые зонды, тестовые метки, старое имя переименованного отправителя. Каждая такая метка иначе станет наблюдаемым отправителем и начнёт алертить — с точки зрения шаблона она и есть замолчавший отправитель.

   ```sh
   curl -s "$VL_URL/select/logsql/query" \
     --data-urlencode 'query=_time:>now-90d | stats by (host) max(_time) as last
       | math (now() - last) / 1e9 as age | filter host:* | fields host, age' \
     | jq -r '[.host, (.age|tonumber|floor|tostring)] | @tsv' | sort -k2 -n
   ```

   Метки с большим возрастом — первые кандидаты либо в исключения, либо в расследование: одна из них может оказаться отправителем, который замолчал месяц назад и никем не замечен.
4. Привязать `Vector log shipper by Zabbix agent` к отправителям с Zabbix agent 2.

Порог задержки правится макросом `{$LOG.LAG.WARN}` — **на приёмнике**, не на отправителе, и ключ контекста — это метка в логах. Почему именно так и как это делать точечно для одного шумного хоста — в [docs/operations.md](docs/operations.md).

## Как снять хост с сопровождения

Внести его метку в `{$LOG.LABEL.EXCLUDE}` — **и только потом** глушить шиппер. Обнаружение перестаёт видеть метку, элемент удаляется через 30 дней, тикетов не создаётся.

Обратный порядок — сначала выключить шиппер — даёт тикет: элемент не отключается по потере ресурса, это и есть то свойство, которое делает обнаружение из данных безопасным. Отказ здесь шумный, а не тихий, и это выбрано намеренно: забытое заведение раньше стоило 95 минут незамеченного молчания, забытое снятие стоит одного лишнего тикета.

Временно заглушить одного отправителя — maintenance **на приёмнике** с фильтром по тегу `sender` со значением метки: триггер живёт там, и период обслуживания на самом отправителе на него не действует. Три пути и когда какой — в [docs/operations.md](docs/operations.md).

## Обновление с 1.x

Версия 2.0 меняет источник списка отправителей: группа хостов больше не используется. Импорт шаблона удаляет два элемента (`log.inventory.raw`, `log.inventory.count`), триггер «инвентарь не обновляется», канарейку «отправитель вне группы» и график «registered vs shipping».

**Уже обнаруженные элементы пересоздаются.** Проверено на импорте в работающий эстейт: у `log.age[<метка>]` меняется `itemid`, хотя ключ тот же — правило обнаружения сменило мастера, и прежние ресурсы Zabbix заводит заново. Следствия: история значений за 7 дней по этим элементам теряется, а открытые проблемы по их триггерам закрываются вместе со старыми объектами. Если в момент импорта какой-то отправитель алертил, тикет закроется сам и откроется заново через `{$LOG.LAG.WARN}` — импортировать лучше в тихий момент.

Что сделать руками, по порядку:

1. Разобрать метки в окне и заполнить `{$LOG.LABEL.EXCLUDE}` — **до** импорта, иначе мусорные метки заведутся и заалертят.
2. Перебрать периоды обслуживания с фильтром по тегу `sender`: значение тега теперь метка, а не имя хоста в Zabbix (`ifp-vps02` вместо `IFP-VPS02`), а сравнение точное.
3. Перенести контекстные макросы `{$LOG.LAG.WARN:"..."}`, если они заданы: ключ контекста тоже стал меткой.
4. После импорта удалить то, что перестало быть нужным: группу отправителей, пользователя API, его роль и токен. Шаблон к API Zabbix больше не обращается.

## Чего это не измеряет

Свежесть — не полнота. И отправитель, у которого шиппер стоит, но не доехало ни строки, не существует для этого шаблона вовсе: у него нет метки, значит нечего обнаруживать. Семь известных пределов перечислены в [docs/known-limits.md](docs/known-limits.md).
